# XVII CRM

Веб-приложение для ежедневной работы сервисного центра. Рабочие данные хранятся в общей базе Supabase/PostgreSQL, а вход и права сотрудников обслуживаются Supabase Auth и Row Level Security (RLS). В приложении нет фиктивных клиентов или заказов: новые записи появляются только после сохранения в подключённый проект.

В XVII доступны светлая и тёмная темы: переключатель находится в верхней панели, выбор сохраняется в браузере.

Новые компании получают 14 дней пробного доступа. Тарифы: 399 ₽ за месяц, 1 125 ₽ за 3 месяца, 2 250 ₽ за 6 месяцев и 4 500 ₽ за год. Оплата и пополнение баланса проходят через ЮKassa; баланс можно расходовать на любой тариф. Включение автопродления требует отдельного согласия, а отключить его можно в XVII.

## Подключение общей облачной базы

XVII работает как многопользовательский SaaS: все компании и их сотрудники используют один Supabase-проект, а данные разделены по организациям через PostgreSQL Row Level Security (RLS). URL проекта не вводится при каждом входе и не нужен сотрудникам.

1. Создайте проект в Supabase и дождитесь его запуска.
2. Откройте **SQL Editor → New query**, примените базовую миграцию `supabase/migrations/202610090001_qos_crm.sql`, затем по порядку примените миграции `202610090002`–`202610090009` и `202610100001`–`202610100004` из папки `supabase/migrations`. Дождитесь успешного результата до регистрации первого пользователя. Для уже настроенной базы примените только новые миграции, которые ещё не запускались.
3. В Supabase откройте **Authentication → Providers → Email** и включите вход по электронной почте. При подтверждении адресов оставьте подтверждение включённым и подтвердите адрес владельца из письма Supabase.
4. Откройте **Project Settings → API**. Скопируйте Project URL и только публичный ключ **anon/public** или **publishable**. В файле `qos-config.js` укажите их в `supabaseUrl` и `supabaseAnonKey`. Этот файл загружается браузерами всех пользователей, поэтому указывайте только публичный ключ с включённым RLS; никогда не вставляйте `service_role`/secret key.
5. Для локального запуска выполните из папки проекта в PowerShell:

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\serve.ps1
   ```

   Откройте `http://127.0.0.1:8080/`. После настройки `qos-config.js` выберите «Создать компанию» и зарегистрируйте владельца. Создаётся только компания; владелец попадёт на приветственный экран и сможет создать нужный филиал. Сотрудники входят по рабочей почте и паролю — URL Supabase им не нужен. При добавлении сотрудника назначьте конкретный филиал или выберите «Все филиалы».
6. Для работы с других устройств опубликуйте статические файлы проекта на HTTPS-хостинге (например, на своём веб-сервере или статическом хостинге). Не используйте локальный PowerShell-сервер как публичный сервер. В **Authentication → URL Configuration** добавьте адрес опубликованного приложения в **Site URL** и **Redirect URLs**.
7. После регистрации владельца отключите публичную регистрацию по почте в настройках Supabase Auth, если не хотите, чтобы посторонние создавали отдельные компании в том же проекте. Сотрудников владелец добавляет из раздела «Сотрудники»; другим сотрудникам это можно разрешить отдельно.

Настройте `qos-config.js` и примените миграции до регистрации первого владельца. Пустой шаблон не подключится к облаку: приложение покажет сообщение, что XVII Cloud ещё не настроен. Миграция `008` отключает автоматическое создание филиала «Центральный»; существующие записи и назначения сотрудников со стандартного филиала сохраняются, но переводятся в режим «Все филиалы».

Владельцы и сотрудники с правом управления подпиской могут переключаться между всеми филиалами независимо от старого назначения филиала в профиле. Для сотрудников, закреплённых за филиалом и не имеющих этого права, доступ по-прежнему ограничен назначенным филиалом. Миграции `202610100001_manager_branch_scope.sql` и `202610100002_manager_branch_record_creation.sql` применяют это правило и серверную проверку филиала в PostgreSQL.

Права сотрудников сохраняются защищённой функцией PostgreSQL `update_member_permissions`; примените миграции `202610100003_update_member_permissions_rpc.sql` и `202610100004_fix_permission_persistence.sql`, чтобы не зависеть от версии опубликованной Edge Function `manage-users`. После каждого сохранения приложение перечитывает права из базы и сверяет их с выбранными. Назначать права может только владелец компании; менеджер видит только разрешённые ему разделы. Каждый пользователь также может выбрать акцентный цвет в верхней панели; настройка хранится локально в его браузере и не меняет оформление коллег. Тёмная тема использует контрастные светлые подписи, поля и переключатели.

## Управление сотрудниками

Для списка, создания, блокировки и удаления пользователей нужен защищённый Edge Function `manage-users`:

1. В Supabase откройте **Edge Functions** и создайте функцию с именем `manage-users`.
2. В редактор функции вставьте содержимое `supabase/functions/manage-users/index.ts` и опубликуйте функцию. Оставьте включённой проверку JWT (`verify_jwt = true`).
3. Проверьте в **Edge Function secrets**, что доступны `SUPABASE_URL`, `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY`. Секретный ключ задаётся только в Secrets проекта Supabase; не помещайте его во фронтенд, HTML, локальное хранилище или публичный репозиторий.

После обновления XVII повторно опубликуйте `manage-users/index.ts`: функция явно закрепляет созданного сотрудника за организацией, ролью и назначенным филиалом. Если сотрудник уже оказался владельцем отдельной пустой организации, откройте **Сотрудники → Восстановить доступ** и укажите его почту, роль и филиал. Перенос выполняется только когда в прежней организации нет других сотрудников и CRM-данных, кроме автоматически созданного основного филиала.

Если функция недоступна, CRUD записей в других разделах продолжит работать, но список сотрудников, приглашение, блокировка и удаление пользователей завершатся явной ошибкой. Если интерфейс сообщает, что `manage-users` не опубликована, проверьте имя функции и публикацию. Для ошибки сети `Failed to fetch` дополнительно проверьте URL проекта и CORS/доступность Edge Functions; не отключайте JWT и не добавляйте `service_role` в приложение.

## Индивидуальные права доступа

Миграция `202610090009_individual_permissions.sql` добавляет права каждого сотрудника в `organization_members.permissions` и проверяет их на стороне PostgreSQL через RLS и защищённые RPC. После её применения владелец открывает **Настройки → Права доступа**, выбирает сотрудника и отдельно включает просмотр, создание, изменение, удаление, импорт и экспорт для каждого раздела. Оплата заказов, печать талона, управление сотрудниками, настройка талона и управление подпиской выдаются отдельными флажками. Менять матрицу может только владелец компании; владелец всегда сохраняет полный доступ.

Существующие и новые сотрудники получают безопасный минимум: просмотр разделов без права менять данные. Настройки вступают в силу на сервере сразу; сотруднику следует обновить страницу или войти повторно, чтобы интерфейс перезагрузил его текущую матрицу прав. После применения миграции опубликуйте актуальную `manage-users/index.ts` и `qos-billing/index.ts`: первая ограничивает управление сотрудниками и изменение матрицы, вторая проверяет разрешение на операции с подпиской.

## Исправление `organization_id is ambiguous`

Если базовая миграция уже применена, не запускайте её повторно. Файлы `supabase/migrations/202610090002_fix_ambiguous_organization_id.sql` и `supabase/migrations/202610090003_fix_ambiguous_record_creation.sql` обновляют только серверные функции и не меняют существующие таблицы или записи. Чтобы устранить ошибки неоднозначной ссылки и при оплате, и при создании записей, выполните оба файла по отдельности в **SQL Editor → New query**.

Миграция `202610090002` исправляет функцию проведения оплаты. `202610090003` исправляет функцию создания записей. Для актуальной версии XVII также выполните миграции `202610090004_order_contacts_and_costs.sql`, `202610090005_move_records_on_branch_delete.sql`, `202610090006_split_order_payments_and_close_guard.sql` и `202610090007_billing_trials_and_wallet.sql` по отдельности в **SQL Editor → New query**. Миграция `004` добавляет клиента из заказа в той же транзакции. Миграция `005` атомарно переносит записи и назначения сотрудников при удалении филиала. Миграция `006` добавляет предоплату, раздельный учёт наличных и безналичных платежей и запрет закрытия заказа до полной оплаты. Миграция `007` запускает trial на 14 дней, подписки, баланс и блокировку доступа к рабочим данным после окончания оплаченного периода. Для уже созданных компаний 14-дневный пробный период начинается при применении миграции `007`. После выполнения обновите XVII. Если базовая миграция ещё не запускалась, выполняйте файлы по порядку: `001`, `002`, `003`, `004`, `005`, `006`, `007`.

## Подписки и ЮKassa

Для биллинга требуется применить миграцию `202610090007_billing_trials_and_wallet.sql` и опубликовать функцию командой `supabase functions deploy qos-billing` из связанного с проектом Supabase каталога. При ручном создании функции в Dashboard отключите для неё **Verify JWT**: функция принимает webhook ЮKassa, а пользовательские действия сама защищает проверкой JWT, членства и роли. В Supabase **Edge Function Secrets** задайте:

- `YOOKASSA_SHOP_ID` — идентификатор магазина ЮKassa;
- `YOOKASSA_SECRET_KEY` — секретный ключ магазина;
- `QOS_BILLING_RETURN_URL` — полный адрес приложения XVII, например `https://crm.example.ru/`;
- `QOS_BILLING_CRON_SECRET` — длинный случайный секрет для планового запуска автопродлений;
- стандартные `SUPABASE_URL`, `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY`.

Не добавляйте секреты ЮKassa, `service_role` или секрет планировщика в браузер, HTML, публичный репозиторий или переменные фронтенд-сборки. Функция `qos-billing` настроена с `verify_jwt = false`, потому что она принимает уведомления ЮKassa; для пользовательских операций функция сама проверяет access token и право владельца либо сотрудника с выданным `billing.manage`, а каждое уведомление дополнительно подтверждает запросом платежа к API ЮKassa.

В личном кабинете ЮKassa настройте HTTP-уведомления `payment.succeeded` и `payment.canceled` на `https://<PROJECT_REF>.supabase.co/functions/v1/qos-billing`. После оплаты пользователя вернёт на адрес `QOS_BILLING_RETURN_URL`; факт зачисления определяется только подтверждённым уведомлением ЮKassa, а не перенаправлением браузера.

Для автоматического списания настройте ежедневный HTTP-запуск POST-запроса на `https://<PROJECT_REF>.supabase.co/functions/v1/qos-billing` с JSON-телом `{"action":"process-renewals"}` и заголовком `x-cron-secret: <QOS_BILLING_CRON_SECRET>` (например, через Supabase Cron/Edge Function Schedules или доверенный внешний планировщик). Запуск заранее создаёт платёж сохранённым в ЮKassa методом; уведомление провайдера активирует новый период. Автопродление включается только по отдельному согласию при оплате картой. Пользователь может отключить его в XVII; при неуспешной попытке продления планировщик повторяет попытку при следующем запуске до даты окончания подписки.

В разделе **Подписка и баланс** владелец или сотрудник с разрешением `billing.manage` может оплатить план напрямую, оплатить его с внутреннего баланса или пополнить баланс на сумму от 100 до 50 000 ₽. Сотрудникам без этого права доступен только просмотр.

## Оплата и закрытие заказов

Оплата заказа поддерживает предоплату: в карточке можно внести часть суммы или распределить платёж между наличными и безналичными. Каждый вид оплаты отдельно попадает в журнал финансов, а при внесении полной суммы заказ автоматически получает статус «Закрыт». Статусы «Выдан» и «Закрыт» нельзя установить до полной оплаты; это правило дополнительно проверяется PostgreSQL. Миграция `006` восстанавливает историю раздельных оплат по журналу платежей, где это возможно.

В карточке заказа доступны поле заметок и история комментариев. Новый комментарий сохраняется с датой, временем и именем сотрудника.

## Клиенты и расчёт себестоимости

При сохранении заказа XVII автоматически добавляет клиента в раздел «Клиенты» в той же филиальной базе. Совпадение по нормализованному телефону или адресу электронной почты предотвращает повторное создание карточки. Чтобы исключить дубли, указывайте хотя бы один контакт; без контакта клиент из заказа всё равно добавляется как отдельная запись.

В заказе указываются цена для клиента и себестоимость ремонта/запчастей; прибыль считается как их разница только после ввода себестоимости. Пока она не указана, прибыль остаётся пустой и не включается в сумму учтённой прибыли. Себестоимость заказа вводится вручную: списание складских товаров и добавление их стоимости в заказ автоматически пока не связаны. Для складской позиции отдельно указываются себестоимость единицы и цена продажи, а оценка стоимости запасов считается по себестоимости. Старые складские позиции сохраняют прежнее поле `price` как цену продажи; себестоимость для них нужно заполнить вручную, так как её нельзя достоверно восстановить из прежних данных.

## Возможности

- **Обзор:** фактические суммы операций из базы, последние заказы, кассовые поступления наличными/безналично и предупреждения о минимальных складских остатках.
- **Заказы:** сквозной автоматический номер от № 1 для каждой компании, редактирование, статусы, просмотр карточки, приём частичной или полной оплаты и поиск.
- **Формы заказов и записей:** клиента можно выбрать из базы с автозаполнением телефона и почты, ответственного — из списка сотрудников; дата заказа и дата записи по умолчанию сегодняшние. Устройство, комплектность и категория подсказываются по ранее внесённым данным; статус и время выбираются из удобных меню.
- **Платежи:** выбор наличного/безналичного способа; регистрация оплаты и запись в журнал доходов происходят одной транзакцией на сервере. Связанные с заказом операции в журнале нельзя случайно изменить отдельно.
- **Клиенты, задачи и календарь:** создание, просмотр, редактирование, удаление и поиск.
- **Склад:** товары, артикулы, количество, единицы измерения, минимальный остаток и цены.
- **Финансы, услуги, документы и филиалы:** постоянные записи с редактированием и контролем доступа на сервере.
- **Управление филиалами:** создание, изменение и удаление филиалов настраиваются отдельными правами. При удалении связанные записи и назначения сотрудников автоматически переходят в другой филиал; последний филиал удалить нельзя. Если филиалов нет, обзор предложит создать первый.
- **Команда:** роли владелец, администратор, менеджер, мастер и кассир; добавление пользователя с временным паролем, блокировка/разблокировка и удаление аккаунта.
- **Талон приёма:** общие настраиваемые для компании поля и текст, печать на принтер или сохранение в PDF. В талоне показываются товары и услуги заказа, количество, цена для клиента и итог; себестоимость клиенту не раскрывается.
- **Каталоги услуг и товаров:** при создании заказа доступно меню с поиском и отдельными вкладками услуг и товаров выбранного филиала. Товар можно создать прямо из меню, а цену и себестоимость существующего товара или услуги — изменить. Выбранные позиции показывают цену и себестоимость; количество и цену каждой позиции можно изменить прямо в заказе, итог и ожидаемая прибыль пересчитываются. Категории сохраняются и предлагаются при повторном вводе, а расположение товара выбирается из филиалов и уже заведённых складов, а не вводится вручную. У услуги в прайсе задаются цена клиенту и себестоимость.
- **CSV:** импорт и экспорт поддерживаемых таблиц; импорт ограничен 5 МБ и 500 записями за операцию.
- **Изоляция компаний:** политика RLS, проверка прав и атомарные финансовые операции в PostgreSQL. Данные не переключаются на фиктивный или локальный демо-набор при ошибке облака.
- **Филиалы:** записи видны с учётом назначенного филиала; переключение филиалов доступно сотрудникам без закреплённого филиала и с правом просмотра филиалов. При удалении все записи и назначения сотрудников атомарно переходят в другой филиал; удалить последний филиал нельзя.

Разделы сообщений и отзывов не отображаются. Интеграции SMS и мессенджеров, реальные банковские эквайринговые платежи и перенос данных из сторонних CRM не входят в текущую версию.

## Роли и доступ

- **Владелец:** полный доступ; только владелец меняет индивидуальные права сотрудников.
- **Администратор, менеджер, мастер и кассир:** роль отображается в профиле, а фактические права задаются владельцем отдельно для каждого сотрудника во вкладке **Настройки → Права доступа**. Роль сама по себе не даёт права создавать, изменять или удалять записи.

Ограничения проверяются политиками и функциями PostgreSQL, а не только видимостью кнопок. Публичный ключ Supabase предназначен для браузера; безопасность записей обеспечивается RLS. Токен входа хранится в `sessionStorage` и удаляется после закрытия вкладки.

## Структура

- `index.html` — каркас приложения и навигация.
- `src/styles/main.css` — дизайн-система и адаптивные стили.
- `src/js/app.js` — интерфейс, навигация и сценарии CRM.
- `src/js/data/schemas.js` — описания полей, столбцов и названий рабочих разделов без тестовых записей.
- `src/js/modules/` — отдельные экраны обзора, списка, команды, авторизации и шаблона квитанции.
- `src/js/services/supabase.js` — аутентификация и HTTPS API-клиент Supabase.
- `src/js/services/crm-repository.js` — общая граница доступа к данным CRM.
- `src/js/utils/csv.js` — безопасный импорт и экспорт CSV.
- `supabase/migrations/` — структура базы, RLS и серверные атомарные операции.
- `supabase/functions/manage-users/` — защищённое управление учетными записями сотрудников.

На странице «Обзор» кнопка «Продажа» открывает быструю форму поступления с сегодняшней датой и выбором наличной или безналичной оплаты. График показывает дневные поступления отдельно по способам оплаты; наведите курсор или переведите фокус клавиатурой на столбец, чтобы увидеть дату, суммы и число платежей.

## Важные ограничения запуска

Локальный запуск служит только для проверки интерфейса на этом компьютере. Для совместной работы пользователи должны открывать один и тот же HTTPS-адрес приложения и подключаться к одному Supabase-проекту. До настройки проекта, применения миграции, публикации функции сотрудников и проверки рабочего окружения приложение нельзя считать развёрнутой CRM компании. Храните резервные копии данных Supabase и отдельно проверяйте восстановление перед реальным использованием.
